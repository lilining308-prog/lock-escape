## 尚未解除的分发缺口

- `0.1.0` 两个历史 APK 内没有 GPL/第三方声明，且最初包含二进制的提交中没有 `LICENSE`；当时 `README.md` 曾把无法核实许可的 PhoneGuard 和 wasted 列作参考。保留历史文件不等于已向获取者补发许可和源码，也无法仅凭后来修正文档证明早期代码没有复用未授权实现。
- 对 `0.1.0` 的源码归属与实际分发范围，需要依据原始构建记录/作者材料进一步核实；本地 Git 历史和 APK 内容不足以代替这些证据。
- 三组 `2.0` APK 内附的旧版 NOTICE 与目前修订版不同；仓库文件的改动不会改变已经发布的二进制。表中的 `2.0` 正式包、SU 直启包和 release 包字节完全相同，区别仅是文件名，不能把它们解释为不同构建。
- 上表只验证字节相同的别名和首次出现的 Git 提交，尚未验证这些提交构建出的 APK 与表中二进制相同，也未核实所有历史获取者能取得对应源码及依赖声明。因此目前不能据此宣称所有历史分发均已完全合规。
- 旧版 `SOURCE_PATHS.md` 只指向随时间变化的 `main`，没有标注该 APK 的固定源码提交；本表提供查找线索，但在确证对应构建源码之前，不应对该旧包作“已满足 GPL-3.0 对应源码提供义务”的结论。

## 分发核对

对于旧版二进制，已在仓库文档中停止把它们当成“当前构建”宣传；若仍提供下载，须先确认对应源码、许可与可获取途径，并在下载处直接给出。已有下载链接和历史获取者不因本表的补充而自动得到材料。

1. 对实际提供的 APK 计算 SHA-256，按哈希核对对应源码版本，避免把不同内容的 APK 当成同一版本。
2. 下载页面同时提供该 APK 所对应的完整源码或固定提交及可获得源代码的明确方式，不能仅指向不断变化的 `main`。
3. 一并提供 `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md` 和依赖的许可声明；对于 APK 内未附许可材料的历史版本，必须在包外补齐。
4. 若修改上游 GPL/Apache 代码，保留原作者声明、记录修改日期，满足 GPL-3.0 和 Apache-2.0 的修改声明要求。
5. 涉及第三方 AndroidX、Material、Kotlin 和 Shizuku 库时，按实际 APK 依赖清单逐项核对其版权与许可文本；本仓库目前未提供逐一核验过的完整依赖许可清单，不能把根目录 `NOTICE` 当作全部依赖已核验的证明。
6. 新构建的 APK 必须与同时提供的源码版本绑定；本地未提交源码只随本机存在，不会自动到达下载者。

核对已发布版本是否合规，需要实际向获取者提供上述材料并能证明材料与其 APK 对应；只在本地更新仓库文本无法追溯修复已经发生的分发。
